# fixwitness 0.5: development and evaluation protocol

Written and committed on 23 November 2026, **before any 0.5 code change**. The git history shows the order.

## Why there is a 0.5

fixwitness 0.4.0 accepted all 7 wrong fixes in the assistant study (`study/README.md`). Diagnosis:

| Class | Wrong fixes | What 0.4.0 never generates |
|---|---|---|
| Schema drift | I05: ChatGPT, Claude, Gemini | A file the job already handled that also contains another column, such as the new column from the incident file (`amount_usd`) |
| Header text | I07: Claude, Gemini, Copilot | A header with other delimiter characters, quotes or a line break in a column name |
| Delimiter characters inside values | I07: ChatGPT | A text value that combines another delimiter character with CSV quotes |

0.4.0 varies only cell values in the sample's existing columns, plus a header-only file and CRLF line endings. The header row, the set of columns and their order never change.

## What 0.5 may add

**Allowed:** general input classes, generated by rule from the user's sample and incident file:
- extra columns, including every column that appears in the incident file but not in the sample, at the start and at the end of the header;
- columns in a different order;
- extra columns whose names contain other delimiter characters (`;`, tab, `|`), with enough of them to outnumber the commas in that header line, plus quotes, a line break, Unicode, spaces and an empty name;
- text values that combine another delimiter character with CSV quotes.

All new cases are `valid` cases: the fix must give the same output as the original wherever the original succeeds. Inputs the original fails on stay "not comparable", as in 0.4.0.

**Not allowed:** rules or strings written for a particular benchmark case or assistant fix. Examples are copying the exact inputs from `study/labels.csv`, or special-casing column names from one benchmark case.

## Development results (reported as development, not as evaluation)

The 92 existing fixes (56 benchmark, 36 assistant) are the development set. 0.5 was designed after seeing their results, so they cannot measure how well 0.5 generalises. Success criteria on them, fixed now:

1. All 7 wrong assistant fixes are rejected.
2. None of the 29 correct assistant fixes are rejected.
3. None of the 21 correct benchmark fixes are rejected.
4. At least 29 of the 35 wrong benchmark fixes are still rejected (no regression).
5. All unit tests pass, including new tests for each new input class. The three bundled examples give the same verdicts as in 0.4.0.

If any criterion fails, the result is reported as it is, and either the release waits or the README states the failure.

## Held-out evaluation (the number to publish)

1. **Freeze the tool:** tag `v0.5.0` before any held-out task is written.
2. **Write 10 new incident tasks** in the same format as I01–I09, each with an original, a sample, an incident file and an expected output. They must not reuse any of I01–I09's failure types, and they are committed before any assistant sees them.
3. **Collect fixes:** the author runs the prompt in fresh chats with assistants (12 chats planned). Answers are saved unchanged, with model and date, following the capture rules in `study/README.md`.
4. **Label before scoring:** every fix is labelled correct or wrong by the same rule as before (process the incident input correctly without changing the output for any input the job already handled), with a reproducing input for every "wrong". This uses `label_check.py` and code review, and the author approves the labels **before** fixwitness 0.5 is run on these fixes.
5. **Score:** run the four checks (job runs, sample test, fixwitness, fixwitness + expected output) and report every miss and every false alarm.

The tool is not changed between steps 1 and 5. Any later change is a new version, evaluated on new held-out tasks.
